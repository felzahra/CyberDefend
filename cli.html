Lab Overview: High Availability, Policies & NAT

Welcome to the advanced Firewall Lab! In this exercise, you will configure two different vendor firewalls for High Availability (HA), create Security Policies (Permit/Deny), and configure Network Address Translation (NAT) to allow traffic to flow securely.

Figure 1: A redundant network infrastructure. Two firewalls act as one logical unit.
Key Concept: Traffic Flow
Traffic flows from the Internet (WAN) -> Firewall -> Core Switch -> Internal Zones.
1. NAT translates private IPs to public IPs.
2. Policies act as bouncers, deciding which traffic is permitted (allowed) or denied (blocked).

Part 1: FortiGate Active-Active HA

Scenario: Two FortiGate 600Cs configured for Active-Active HA. Master Priority: 110, Slave Priority: 100. Heartbeat links are port3 and port4.

Step 1: Configure HA Heartbeat and Mode

FGT-MASTER (CLI)
FGT-MASTER # config system ha set group-name "FGT-HA" set mode a-a # Active-Active set hbdev "port3" 50 "port4" 50 set session-pickup enable set priority 110 # Master wins election set monitor "port11" "port13" FGT-MASTER (ha) # end
Student Task: Run this on the Slave firewall, but change priority to 100.

Step 2: Configure Dedicated Management & Redundant IPs

FGT-MASTER (CLI)
# Dedicate mgmt1 so it doesn't sync IPs FGT-MASTER # config system ha set ha-mgmt-status enable set ha-mgmt-interface "mgmt1" FGT-MASTER (ha) # end # Configure Floating IPs on Master (Syncs to Slave) FGT-MASTER # config system interface edit "port11" # WAN set ip 41.33.25.10 255.255.255.128 next edit "port13" # Inside to Core Switch set ip 10.0.251.254 255.255.255.0 next FGT-MASTER (interface) # end

Part 2: Juniper SRX Chassis Cluster

Scenario: Two SRX firewalls linked by a Fabric cable. Node 0 is Primary (100), Node 1 is Backup (1).

Step 1: Enable Cluster & Redundancy Groups

SRX-CLUSTER (CLI)
# Run on Node 0 shell: set chassis cluster cluster-id 1 node 0 reboot root@cluster# set chassis cluster reth-count 10 root@cluster# set chassis cluster redundancy-group 0 node 0 priority 100 root@cluster# set chassis cluster redundancy-group 1 node 0 priority 100 root@cluster# set interfaces fab0 fabric-options member-interfaces ge-0/0/0 root@cluster# set interfaces fab1 fabric-options member-interfaces ge-4/0/0 root@cluster# commit

Step 2: Configure RETH Interfaces & Zones

SRX-CLUSTER (CLI)
# Create reth1 (External Zone) and assign physical ports to it root@cluster# set interfaces reth1 redundant-ether-options redundancy-group 1 root@cluster# set interfaces reth1 unit 0 family inet address 10.0.251.1/24 root@cluster# set interfaces ge-0/0/1 gigether-options redundant-parent reth1 # Assign interface to Security Zone root@cluster# set security zones security-zone external interfaces reth1.0 root@cluster# commit

Part 3: Security Policies & NAT (Permit/Deny)

Now that HA is configured, we must write rules to allow or block traffic. We also need NAT to translate private IPs to public IPs.

Figure 2: Traffic flowing through the firewall based on Permit/Deny rules.

Step 1: FortiGate Policies & VIP (Destination NAT)

We will create a Virtual IP (VIP) to map our public WAN IP to a private internal Web Server. Then, we write a policy to permit internet users to access it. Finally, we block Guest Wi-Fi from accessing the internal network.

FGT-MASTER (CLI)
# 1. Create Destination NAT (VIP) for Web Server FGT-MASTER # config firewall vip edit "WebServer_VIP" set extip 41.33.25.10 set mappedip 10.0.10.44 # Internal Server IP set extintf "port11" next FGT-MASTER (vip) # end # 2. Policy: PERMIT Internet to Web Server (Port 80) FGT-MASTER # config firewall policy edit 1 set name "Allow_Inbound_Web" set srcintf "port11" set dstintf "port13" set action accept set srcaddr "all" set dstaddr "WebServer_VIP" set service "HTTP" set schedule "always" next # 3. Policy: DENY Guest Wi-Fi to Internal Network edit 2 set name "Block_Guest_to_Inside" set srcintf "port10" # Guest Port set dstintf "port13" # Inside Port set action deny set srcaddr "all" set dstaddr "all" set service "ALL" set schedule "always" next FGT-MASTER (policy) # end
Student Note: In FortiGate, if action is set to accept and nat is not explicitly set, it uses the routing table to determine if Source NAT is needed. For Destination NAT, the dstaddr must point to the VIP object, not "all".

Step 2: Juniper SRX Policies & Source NAT

We will configure Source NAT so internal users can browse the internet. Then, we will create a security policy to permit outbound traffic, and explicitly deny the Wireless zone from accessing the Server Management zone.

SRX-CLUSTER (CLI)
# 1. Configure Source NAT (Internal to External) root@cluster# set security nat source rule-set NAT_Outbound from zone internal root@cluster# set security nat source rule-set NAT_Outbound to zone external root@cluster# set security nat source rule-set NAT_Outbound rule 1 match source-address 10.0.250.0/24 root@cluster# set security nat source rule-set NAT_Outbound rule 1 then source-nat interface # 2. Policy: PERMIT Internal to External (Internet Access) root@cluster# set security policies from-zone internal to-zone external policy Allow-Outbound match source-address any root@cluster# set security policies from-zone internal to-zone external policy Allow-Outbound match destination-address any root@cluster# set security policies from-zone internal to-zone external policy Allow-Outbound match application any root@cluster# set security policies from-zone internal to-zone external policy Allow-Outbound then permit # 3. Policy: DENY Wireless-RDT to Server-Mgt root@cluster# set security policies from-zone Wireless-RDT to-zone server-mgt policy Block-Wireless match source-address any root@cluster# set security policies from-zone Wireless-RDT to-zone server-mgt policy Block-Wireless match destination-address any root@cluster# set security policies from-zone Wireless-RDT to-zone server-mgt policy Block-Wireless match application any root@cluster# set security policies from-zone Wireless-RDT to-zone server-mgt policy Block-Wireless then deny root@cluster# commit
Concept Check!
Notice how SRX separates NAT configuration from Policy configuration. You build the NAT rule-set first, but traffic won't match it until you write a Security Policy that permits the traffic between those two zones!

4. Lab Summary & Student Notes

HA & Floating IPs

Both firewalls use Floating IPs. Active node owns the IP. If it dies, standby takes it. Users never notice a downtime.

Security Policies

Policies act as gatekeepers. Default action is usually DENY. You must explicitly write rules to PERMIT traffic from one zone to another.

Source NAT (SNAT)

Translates a private IP (e.g., 10.0.0.5) to a public IP (e.g., 41.33.25.10) so internal users can reach the internet.

Destination NAT (DNAT)

Translates a public IP to a private IP. Used when hosting a web server inside your network that needs to be accessible from the internet.
